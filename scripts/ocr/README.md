# Local OCR trial

## Experimental contrast and multiline review

Adopted November 27 as a local review-only fallback: existing suggestions return first; only no-proposal/mobile-enabled cases can run one contrast detection. A six-second additional budget includes health, preprocessing, inference and remaining catalog time. Busy/offline/timeout cases preserve manual correction/barcode review. The helper now lives in lib/contrast-review.ts and this directory re-exports it for benchmark reproducibility. Live automatic identification and stock/ISBN rules are unchanged. Read-only saved-photo checks confirm Catcher review and preserved Kafka suggestions; a fresh Discord acceptance check is separate. Run `npx tsx scripts/test-cover-review.ts` for ordering, deadline and concurrency regressions. Historical experimental results below explain why this is an additional stage, not a replacement.

Run `npx tsx scripts/ocr/contrast-benchmark.ts` with the local worker ready and the validated 28-photo corpus present. It validates input hashes, performs fresh same-size RGB/green detections on every photo and evaluates exact work evidence and review proposals. Then run `npx tsx scripts/ocr/contrast-policy-check.ts` to compare existing review proposals with a fallback-only selection using the saved experiment. These scripts use read-only catalogs and no database/import/Discord operations. Reports stay private under .folio-ocr; they do not activate a bot policy.

The November 27 trial preserved six existing review cases and added vintage Catcher only when existing suggestions were tried first. Mixing all extra OCR into existing searches lost Kafka's proposal; do not replace that search input wholesale. Two covers remain unresolved. Nineteen earlier automatic paths were preserved by stage ordering, not freshly measured. Additional green preprocessing/inference median was 1409 ms; catalog and startup time are separate. Run `npx tsx scripts/test-contrast-review.ts` for experimental geometry/negative-evidence checks. The helper remains under scripts/ocr and is not used by the live bot.

## Enable the tested local policy

The managed worker allows up to 180 seconds for model initialization, separately from its 27-second per-scan bridge timeout and 25-second Python watchdog. Model loading keeps the bridge heartbeat alive while readiness remains false; Tesseract remains available during warm-up. Logs distinguish startup timeouts, inference timeouts and unexpected process exits, and record successful model-load duration. Run `npx tsx scripts/test-ocr-worker-lifecycle.ts` for the simulated lifecycle regression without WSL or inventory access.

Activation waits for the previous supervisor to finish shutting down before starting its replacement. A refused stale control endpoint is recoverable only when the recorded owner is provably dead; live or inaccessible owners are preserved. A preflight PASS followed by a startup-control error does not mean the models failed and does not confirm that mobile mode is active. Rerun `ocr:enable` after resolving that specific startup error; wait for the final managed-worker PASS line.

The activation smoke check sends a full synthetic canvas to detection and a tightly trimmed text line to recognition-only inference. Failed text checks report the synthetic recognized text/confidence; `.folio-local/ocr-smoke-check.json` keeps those synthetic diagnostics without uploaded covers. A failed preflight leaves the mode unchanged.

Run `npm run ocr:enable` in the operator's Folio PowerShell. It starts a private persistent mobile worker, runs two synthetic scans and direct-line recognition without catalog/database/Discord access, checks that the primary model stayed loaded, then enables `.folio-local/ocr-enabled` and restarts the local services. Cached models and the existing WSL environment are reused; missing setup must be completed with the trial installer first. Wait for the final PASS line. `npm run local:status` reports worker readiness/degraded mode. PC shutdown/sleep still pauses local imports; the existing Windows startup task restores the supervised worker at logon. `npm run ocr:check` tests readiness/inference without changing the mode; `npm run ocr:disable` restores Tesseract and restarts services. No credentials, URLs or ports need manual copying.

The persistent engine accepts one job at a time and writes no photo files. The application tries mobile first, Tesseract on no-match/unavailability, then the shared crop code on an unresolved scan. It preserves earlier successes; uncertain catalog identity stays unresolved for the existing barcode/operator flow. Model, job and whole-recognition deadlines are separate. A local worker outage is shown as degraded mode and uses Tesseract; catalog outages do not trigger extra OCR in mobile mode. These changes do not install OCR in the Cloudflare Worker or change production secrets.

Integration checks: `npx tsx scripts/test-cover-policy.ts`, `npx tsx scripts/test-local-ocr.ts`, and `npx tsx scripts/test-mobile-import.ts`. The latter uses only an isolated PGlite database and a fake inference backend; real model startup is verified by the activation smoke test. Crop preparation/ordering now lives in `lib/cover-geometry.ts` and is shared with the benchmark to prevent rasterization drift.

## Crop and reading-order experiment

The report also evaluates a staged policy: keep the first mobile match; on no-match try the saved Tesseract output, then the saved crop output. It does not choose a stage using expected labels or overwrite a successful earlier match. Catalog exceptions remain outages rather than causing another OCR fallback. Reported policy OCR time sums the measured stages actually attempted (crop incremental time excludes the already-counted mobile baseline); it excludes model startup, catalog and Discord latency. This remains a retrospective policy test with cached OCR, not an active bot integration. Initial geometry measurements were retained separately with the `-initial` suffix before formatter/ordering corrections.

`npm run ocr:geometry` reuses the same frozen photos and cached mobile models. It prepares two overlapping full-width 60%-height crops plus direct-recognition crops for up to six prominent observed rows. Row selection uses only mobile OCR coordinates/confidence, never expected labels or book-specific words. Direct row recognition bypasses detection and uses grayscale/contrast/sharpening; original photo bytes and baselines are retained. Every crop has a hash, dimensions and mapping to original coordinates. Maximum eight additional views per photo, 1,200px longest saved side, detector cap 960, batch one, two CPU threads. These are compute/input bounds, not a guaranteed memory ceiling.

The report separates unchanged mobile, mobile with overlapping regions read left-to-right within each row (no extra OCR), and mobile plus new crops/row reading order. All 28 photos are tested, including existing successes, so regressions count. Raw view readings are retained; no fuzzy spelling, dictionary title guesses, label-based crop selection or automatic engine activation is used. The geometry timing includes saved baseline inference plus newly measured crop inference; startup and peak RSS are separate. This measures always-running extra passes, not a claimed production fallback latency. `paddle-geometry.json`, `comparison-geometry.json`, `group-summary-geometry.json` and `catalog-trace-geometry.json` are separate outputs. Recognition-only row coordinates use their source row as an anchor because that model produces text without a box; detector crops use exact image transforms. These experimental geometry rules are not in the live bot. Run `npx tsx scripts/test-ocr-geometry.ts` for row-order regression tests.

## Stronger recognizer comparison

Run `npm run ocr:stronger` in Folio PowerShell after the mobile trial. It validates the frozen manifest, input hashes and both complete baseline reports, then reuses the installed Python environment. Only the recognizer changes to `PP-OCRv5_server_rec`; the mobile detector, maximum detector side 960, batch size one, CPU/two threads and disabled orientation/unwarping remain the same. The larger model downloads on first use. This tests recognition quality rather than stronger text detection; a region missed by the mobile detector can still fail. The bounds do not guarantee a RAM ceiling; load time and peak process RSS are measured separately.

It does not rerun Tesseract/mobile OCR or collect new photos. Results are written separately to `paddle-stronger.json`, `comparison-stronger.json`, `group-summary-stronger.json` and `catalog-trace-stronger.json`. The three-engine report reruns the same current matcher for all engines using live, throttled catalog reads and records author responses as well as searches. Catalog outages remain distinct from no-match results. Earlier raw OCR/comparison/captured-response files are preserved. Partial stronger runs are marked incomplete and cannot produce a comparison. The runner never changes the bot's engine, imports inventory, sends Discord messages or uploads photos to an OCR service.

The recognizer and batch configuration follow the [versioned PaddleOCR recognition documentation](https://www.paddleocr.ai/v3.3.1/en/version3.x/module_usage/text_recognition.html) and [pipeline API](https://www.paddleocr.ai/v3.3.1/en/version3.x/pipeline_usage/OCR.html).

`npm run ocr:replay` reruns only the matcher against saved raw OCR and exact captured catalog responses. It intercepts every request, never uses the network or imports inventory, writes `.folio-ocr/catalog-replay.json`, and leaves the measured comparison untouched. Missing responses are labelled rather than invented. Because the first trace omitted author responses, Homer uses a separately labelled fixture and is excluded from captured-only totals. Durable regressions run with `npx tsx scripts/test-cover-catalog.ts` and include rejection of unsupported adaptations, collections, arbitrary sequel subtitles, missing author/title evidence and equal-strength duplicate records.

## Expanded corpus

Run `npm run ocr:expand` in the operator's Folio PowerShell window. It first copies up to 100 saved listing photos using database SELECTs and permanent-photo GETs, runs the existing-upload comparison, then downloads the targeted sources in `web-sources.json` and up to six Readings catalog baselines. It does not read customer/order records, replay imports or send Discord messages. Download failures are listed rather than silently counted as test cases. The agent session cannot run WSL or reach the services, so this command requires the operator's working terminal.

Groups are `user-upload`, `web-photo`, and `catalog-baseline`. Web photos were selected for physical books with hands, tables, wear or surrounding environments; generated scenes, mockups and unrelated search results are excluded. Search metadata is only a proposed label: every downloaded image must be visually checked against its claimed title/author and photo type. Contact sheets are written to `.folio-ocr/review/`; collected sources/labels live in `.folio-ocr/collected-cases.json`. After visual verification, set the corresponding `labelStatus` to `verified`, or remove/relabel incorrect entries. Then run `npm run ocr:trial` to test the combined set. The report shows each group separately and excludes pending labels from verified counts. Multiple views of a title do not constitute independent books; exact normalized-image duplicates are skipped and recorded. Existing validated seed images are private immutable copies under `.folio-ocr/seed-inputs/`, not a mutable "latest upload" file.

Web assets stay private for this benchmark and are not published as Folio product images. Downloads are bounded and cached; catalog requests are spaced at least 1.1 seconds apart. Real phone/camera-style photos are the relevant stress test; clean scans are a separate baseline, not a substitute for glare, angles or background clutter. The corpus is a small curated convenience sample, not a representative accuracy guarantee.

Run `npm run ocr:trial` from the Folio PowerShell window. The runner prepares labelled local images, measures the current Tesseract path, then uses Ubuntu/WSL to install an isolated Python 3.12 CPU environment and run PaddleOCR. It finishes by comparing catalog identification through the same read-only matcher. It does not import inventory, send Discord messages, or change the active OCR engine.

Ubuntu prerequisite: `libgomp1` supplies the OpenMP runtime required by Paddle. If it is missing, run `wsl --exec sudo apt-get update` and `wsl --exec sudo apt-get install -y libgomp1` from PowerShell, then repeat the trial. Installation needs the Ubuntu user's password; the runner does not attempt elevated package installation automatically.

The initial samples are the two supplied Durant photos and the saved Little Prince upload, when those files exist. Three images / two books are a smoke test, not evidence to switch engines. Add 30–50 varied real covers before choosing a replacement. Include negative/ambiguous cases and manually inspect raw OCR and any wrong matches.

All images, models, dependency caches and output live in ignored `.folio-ocr/`. These private benchmark copies are retained until explicitly removed; they are independent of the bot's 15-minute temporary-cover expiry. Initial setup downloads uv from the official pinned installer, Python and pinned PaddleOCR/PaddlePaddle dependencies; model weights download on first inference. There are no paid API calls. Catalog reporting sends text search queries to Open Library, not photos.

To add samples, create `.folio-ocr/custom-cases.json`:

```json
[
  {"id":"book-cover-01","image":"C:/private/photos/cover.jpg","expectedTitle":"Expected title","expectedAuthor":"Expected author"}
]
```

Run the trial again after changing samples. IDs must be unique lowercase letters, digits or hyphens. The runner bounds image size/pixels and hashes the dataset and each staged image; stale or mixed results are rejected.

Reports: `cases.json` contains labels and input hashes, `tesseract.json` and `paddle.json` contain raw recognized lines, confidence and timings, `comparison.json` includes title/author word coverage and catalog outcome (`correct`, `WRONG_MATCH`, `no_match`, `catalog_unavailable`, `ocr_error`). Coverage is not accuracy and confidence values are not calibrated across engines. Tesseract timing includes initial plus focused scans and their worker starts. Paddle initialization is separate; its first prediction may include additional cold-start work. Compare these limits before inferring latency improvements. `installed-requirements.txt` records resolved Python dependencies.

The trial uses PaddleOCR 3.3.1 / PaddlePaddle 3.2.2 with PP-OCRv5 mobile detection and English mobile recognition, CPU / two threads, detection longest side capped at 960, recognition batch size one, orientation classifiers and document unwarping disabled. The initial server-model trial failed while attempting a single approximately 9.4GiB allocation; it produced no usable comparison. The mobile configuration is an explicit lighter candidate, not a claim of measured memory usage or superior accuracy. The full input remains available to the pipeline; its detector applies the internal resolution limit. Configuration is stored in the private result and incomplete runs are rejected. The existing bot remains Tesseract until measured results and acceptance justify integration.

Sources: [PaddleOCR versioned API](https://www.paddleocr.ai/v3.3.1/en/version3.x/pipeline_usage/OCR.html), [uv installation](https://docs.astral.sh/uv/getting-started/installation/).
